# 手机扫码打印（云端中转）设计

- 日期：2026-09-29
- 状态：方案已确认（按需连接云端、二维码直接是私有子链接、扫到就打、几个人同时用、打印排队）
- 目标版本：1.0.1（和配置中心一起发布）
- 取代：总设计第 1 节里 Phase 2 的「主进程内 HTTPS 服务、自签证书、token/PIN 认证」方案，原因见第 10 节
- 中转服务地址：代码里不写任何域名。官方安装包默认连接 yterm.cn 上的中转服务；任何人都可以自己部署中转服务，在电脑的设置里填自己的地址（见 7.4）

## 1. 目标与范围

**场景**：偶尔补打。扫码枪不在手边，或者在样衣架旁翻到一件要补标签的样衣，用手机摄像头扫它的二维码或条码，标签从店里电脑接的热敏标签机出来。

**做**：

- 电脑上点「手机扫码」，屏幕显示一个二维码；手机用相机或微信扫它，打开扫码页。
- 手机页面实时取景，**扫到就打**，和扫码枪一样一张接一张；每张的进度和结果列在取景画面下面。
- 电脑按本机的识别规则、加工步骤、模板、防重复窗口打印，和扫码枪扫的完全一样，打印记录的来源记为「手机」。
- 手机网络不稳时不丢、不重：每张是一个幂等的打印任务，断线期间扫的先存在手机上（页面被刷新、被系统回收也还在），连上后补发（见 4.3）。
- **几个人同时用**：多部手机扫同一个二维码加入（最多 5 部），扫到的任务和扫码枪共用一个打印队列，先来先打，一次一张；每部手机只看到自己的任务，排队时显示前面还有几张。
- 摄像头用不了时，可以拍照识别或手动输入。

**不做**：

- 手机上选打印机、改模板或设置。
- 账号体系；局域网直连；电脑断网时的手机扫码（扫码枪不受影响）。

## 2. 使用流程

1. **开始**：在电脑的工作台点「手机扫码」。这时电脑才连接中转服务，生成一个私有链接，并显示成二维码。
2. **加入**：手机用系统相机或微信扫这个二维码，打开扫码页。几个人可以各自扫同一个二维码加入，最多 5 部；电脑上列出已加入的手机，可以移除其中一部。移除之后自动暂停新手机加入，要加新手机时在电脑上点「允许新手机加入」。
3. **扫码即打**：页面上点「开始扫码」打开摄像头（摄像头授权和振动都要在一次点按之后），之后一直取景。扫到一个码就生成一个打印任务发给电脑，手机短振动一下，相当于扫码枪的「嘀」。
   - 同一张标签停在镜头里只打一次；它离开画面 3 秒后再扫到，才算新的一次（见 6.2）。
   - 电脑的防重复窗口照常生效，是第二道防线。
4. **排队与结果**：任务列在取景画面下面，最新的在最上面，依次显示「正在发送」「排队中，前面还有 N 张」「正在打印」和结果。取景框的颜色跟着最新一张的结果变。
   - 成功显示打了哪张（字段摘要）；
   - 「重复扫码，已拦截」带「强制补打」按钮；
   - 缺纸、离线、没选打印机这类故障带「重试」按钮，并振动两下提醒。
5. **结束**，出现以下任一情况时，链接作废、电脑断开中转服务：
   - 在电脑上点「结束」；
   - 二维码显示后 10 分钟没有手机打开；
   - 30 分钟没有扫码；
   - 电脑上的程序退出。

## 3. 架构

```
手机浏览器 ──wss──▶ 反向代理（终结 TLS）──▶ 中转服务（容器）◀──wss── 电脑主进程 ──▶ PrintService ──▶ 热敏标签机
扫码页也由中转服务提供         例如 nginx              只转发            电脑主动连出去
```

| 部分 | 位置 | 职责 |
|---|---|---|
| 协议 | `src/shared/mobile-protocol.ts` | 两层消息的类型、校验函数、常量；中转服务、手机页面、电脑三方共用 |
| 端到端加密 | `src/shared/mobile-crypto.ts` | AES-256-GCM 加解密消息内容（WebCrypto，浏览器和 Node 都能用） |
| 打印结果用语 | `src/shared/print-cues.ts` | 打印结果 → 播报句（`VOICE_CUE_TEXT`）的对应关系；手机页面和界面共用，用词一致 |
| 中转服务 | `relay/src/` | Bun 服务：提供扫码页的静态文件，按会话转发 WebSocket 消息 |
| 扫码页 | `relay/web/` | 手机网页：摄像头、解码、防抖、打印任务的发件箱（存在 `localStorage`）和列表；编排在 `phone-controller.ts`，浏览器能力经接口注入 |
| 电脑端 | `src/main/mobile/` | 连接中转服务、接纳和移除手机、打印队列、调用 `PrintService` |
| 电脑界面 | `src/renderer/` | 标题栏的「手机扫码」按钮和非模态浮层，配置中心「集成」分组里的「手机扫码」页 |

**原则**：

- **中转服务只转发**：不解析消息内容，不做业务判断，不写磁盘。手机的接纳、校验、排队、限流、打印都在电脑上做。中转服务重启后，电脑和手机自动重连，会话照常继续。
- **不改 `core/`**：手机的打印经 `PrintService.submit`，来源 `mobile` 早已在 `PRINT_SOURCES` 和数据库的 CHECK 约束里。
- **界面和协议分开**：「扫到就打」是页面的交互；协议本身按「幂等任务 + 确认 + 背压」设计，不依赖页面怎么用它。

## 4. 会话与安全

### 4.1 私有链接

- 电脑开始一次会话时生成三样东西，都用系统随机数：
  - 会话号 `sessionId`：16 字节；
  - 所有权密钥 `ownerSecret`：16 字节，只在电脑和中转服务之间用；
  - 内容密钥 `key`：32 字节。
- 链接是 `<中转地址>m/#<sessionId>.<key>`，都用 base64url 编码。例如中转地址是 `https://relay.example.com/labelflash/` 时，链接是 `https://relay.example.com/labelflash/m/#…`。
- 会话号和内容密钥放在 `#` 后面：浏览器不会把 `#` 后面的部分发给服务器，所以不会出现在反向代理的日志和 Referer 里。

### 4.2 端到端加密

- 手机和电脑之间的应用消息用 AES-256-GCM 加密：
  - 每条消息用新的 12 字节随机 IV；
  - 附加数据是 `labelflash/1/<方向>/<sessionId>`，方向为 `p2d` 或 `d2p`，防止把一个方向的消息反射回去。
- 中转服务只看得到外层信封（会话号、连接号、消息大小和时间），看不到扫码内容、字段、令牌和打印结果。
- 解密失败的消息直接丢弃，写一条日志。

### 4.3 加入、防重放与幂等任务

- **加入**：
  - 手机连上后发 `hello`，带上本地保存的令牌；第一次没有令牌。
  - 没有令牌的手机是新加入的：电脑给它生成 16 字节的令牌，在 `welcome` 里发回。手机把令牌存在 `localStorage`，键名带会话号。
  - 之后同一部手机重连或刷新页面，都带这个令牌。电脑按常数时间比较令牌，认出是哪部手机，它的任务、打印张数都接着算。
  - 会话里已有 5 部手机（`MAX_PHONES_PER_SESSION`）时，新手机收到 `denied: full`，中转服务断开它。
  - **移除**：电脑上可以移除任意一部手机。它的令牌作废，它排队中的任务不再打印（正在打印的那张照常打完），它收到 `denied: removed` 后被断开。带着作废令牌再来的，一律 `denied: removed`，不能换个连接混进来。
  - **移除后暂停加入**：被移除的人手里还有二维码，换个浏览器（没有令牌）就能以新手机的身份回来。所以移除之后电脑自动暂停新手机加入，新来的收到 `denied: locked`；已加入的手机不受影响。要加新手机时在电脑上点「允许新手机加入」。
  - 二维码可能被拍照外传，所以电脑上的手机列表始终可见；发现不认识的手机就移除，或者结束会话（旧链接立即作废）。
  - **同一个连接又打招呼**（电脑重连后中转服务让手机重新 `hello`）：先解开这个连接和原来那部手机的关系，再按令牌认人，不会留下一直显示在线的幽灵手机。
  - **电脑重连**：中转服务确认会话（`opened`）后，电脑把所有手机标为离线，等中转服务重新通知 `joined`、手机重新 `hello` 再对上号。
- **防重放**（挡住被攻破的中转服务重放旧消息）：
  - `welcome` 里带一个本次连接的随机数 `nonce`。
  - 手机之后的每条 `submit` 都带上这个 `nonce`，以及在本次连接内严格递增的 `seq`。
  - 电脑拒绝 `nonce` 不对、或 `seq` 不大于上一条的消息。重放的旧消息带的是旧 `nonce`；重放 `hello` 得到的 `welcome` 又是加密的，拿不到新的 `nonce`。
  - 加密和解密都是异步的，两端都把收发串成一条链，保证按 `seq` 顺序发出、按收到的顺序处理。
- **幂等任务**（保证网络再差也不丢、不重）：
  - 每扫一张，手机生成一个 16 字节的随机任务号 `job`，和原文一起 `submit`。补打是新任务，有自己的任务号。
  - 电脑按任务号去重：第一次收到就回 `accepted` 并排队打印，打完推 `result`；再收到同一个任务号，只回当前进度（`accepted` / `started`）或已有的结果（`result`），不会再打。
  - 手机把还没拿到结果的任务留在发件箱里：
    - 每次被接纳（`welcome`）后原样重发；
    - 发出后 10 秒没收到 `accepted` 也重发（`JOB_ACK_TIMEOUT_MS`）；
    - 已被接受的任务 30 秒没有任何进展（排队位置、开始打印、结果）也用同一个任务号再问一次（`JOB_STATUS_POLL_MS`），电脑只回当前进度。中转服务在限速、对端刚断开时会丢帧，端到端靠这个补上，不依赖中转服务可靠。
  - 发件箱存在 `localStorage`（按会话一条记录，一天后清掉）：断线期间扫的、页面被刷新或被系统回收前没拿到结果的，重新打开页面后按原来的任务号接着发。会话结束（结束、被移除、链接失效）时清空。
  - 存着令牌的手机刷新页面后，收到 `not-found` 也按「被接纳过」处理，等电脑回来（见 5.3）。
  - 电脑按会话保存任务的结果，最多保留最近 1000 个；更早的任务号即使被重放，也会先被 `nonce` / `seq` 挡住。
- **加入前**：电脑忽略所有 `submit`。

### 4.4 电脑端的校验和限制

- **不信任手机消息**：每条都按协议的校验函数检查字段和类型。扫码内容再经过 `PrintService` 的规范化（1–1000 字符、没有控制字符）。
- **只能打印**：手机只能提交「打印这段内容（可选强制补打）」，不能指定打印机、模板或任何设置。
- **一个队列，先来先打**：所有手机的任务按收到的顺序排成一队，一个打完再打下一个；和扫码枪共用 `PrintService` 的打印队列，电脑前的扫码枪不会被手机插队打乱。
  - 任务被接受时回复 `accepted`，带上前面还有几个任务（`ahead`，包括正在打印的那张）。
  - 队伍往前走时（一张打完、一部手机被移除），电脑给**位置变了的每部手机发一条** `queue`，列出它所有还在排队的任务的新位置。一次打印最多引出「一条结果 + 每部手机一条」，不会因为排队的任务多而刷爆中转服务的限速。
  - 开始打印时发 `started`，打完发 `result`，都只发给提交它的那部手机。
- **背压**：拒绝的任务不执行，手机可以稍后重新提交：
  - 每部手机同时等结果的任务最多 10 个，超出回复 `refused: too-many-pending`，不影响其他手机；
  - 所有手机合计每分钟最多 60 个任务（热敏标签机大约一秒出一张，再快也打不出来），超出回复 `refused: rate-limited`。
- **消息大小有上限**：内层消息的明文最多 32 KiB（`MAX_MESSAGE_BYTES`），加密、编码后加上信封仍远小于 64 KiB 的单帧上限。
  - 结果里的字段摘要最多 10 个字段；规则名、字段名、字段值、失败说明各最多 200 个字符（按字符截断，不拆开汉字）。最坏情况（每个字符都要 JSON 转义）也放得下，由测试保证。
  - 请求里的原文最多 4000 个字符，同样有最坏情况的测试。手机提交前先检查，超长的直接提示，不发出去。
- **设备描述只用于显示**：去掉控制字符、格式字符（含双向文字控制符）和行分隔符，最多 40 个字符；写日志时加引号。

### 4.5 中转服务的防滥用

- **连接**：
  - 只接受 JSON 文本帧，单帧最大 64 KiB；
  - 连接后 10 秒内必须发出第一帧（`open` / `join`），否则断开。
- **频率**：每个连接按令牌桶限速，超出的帧丢弃并回复错误；累计超出 50 次就断开。计时用单调时钟，服务器校时不影响限速和宽限期。
  - 手机每秒 5 帧，突发 22：被接纳时一次发出 hello 加发件箱里的 10 个任务，留一倍余量；
  - 电脑每秒 50 帧，突发 110：重连时一次回复 5 部手机各自的 welcome 和 10 个任务的进度，留一倍余量。
- **容量**：
  - 最多 500 个会话、2000 个连接；满了在升级成 WebSocket 之前就回 HTTP 503（带 `Retry-After`），客户端按退避重连，不会先连上再被关掉；
  - 每个会话最多 10 个手机连接（手机上限的两倍，给刷新页面、换网络时新旧连接的短暂重叠）；
  - 每个来源 IP 最多 20 个连接。来源 IP 取反向代理传来的 `X-Real-IP`；容器端口只映射到宿主机的 127.0.0.1，外面直接访问不到。
- **来源检查**：手机连接的 `Origin` 必须等于中转服务的 `PUBLIC_ORIGIN`（扫码页对外的 origin，部署时必填，没有默认值）。
- **所有权**：
  - 会话号第一次 `open` 时，中转服务记下 `ownerSecret` 的 SHA-256。
  - 电脑断线重连时用同一个 `ownerSecret` 再 `open`，中转服务就接管会话，并关掉旧连接。这样处理了半开连接：旧连接其实已经断了，服务端还没发现。
  - `ownerSecret` 不同的 `open` 回复 `session-taken`。
- **日志**：只记连接事件，不记消息内容，会话号只记前 6 个字符。
- **不泄露内部信息**：服务以生产模式运行，出错时只回「Internal Server Error」，不带堆栈和路径；静态文件的路径里有控制字符（例如 `%00`）的在碰文件系统之前就回 404。

## 5. 协议

所有消息都是 JSON 文本帧，版本号 `MOBILE_PROTOCOL_VERSION = 1`。

### 5.1 外层信封（中转服务能看到）

电脑 ↔ 中转服务，路径 `/ws/desktop`：

| 方向 | 消息 | 说明 |
|---|---|---|
| 电脑 → | `{t:'open', v, session, secret}` | 登记或接管会话 |
| 电脑 → | `{t:'send', phone, body}` | 发给某个手机连接 |
| 电脑 → | `{t:'kick', phone}` | 断开某个手机连接 |
| 电脑 → | `{t:'close', reason}` | 结束会话，`reason` 为 `stopped` / `idle` / `quit` |
| 电脑 → | `{t:'ping'}` | 心跳 |
| → 电脑 | `{t:'opened'}` | 登记成功 |
| → 电脑 | `{t:'joined', phone}`、`{t:'left', phone}` | 手机连接加入、离开；`phone` 是中转服务分配的连接号 |
| → 电脑 | `{t:'recv', phone, body}` | 手机发来的消息 |
| → 电脑 | `{t:'pong'}` | 心跳回复 |
| → 电脑 | `{t:'error', code}` | `version` / `session-taken` / `bad-frame` / `rate-limited` / `server-busy` |

手机 ↔ 中转服务，路径 `/ws/phone`：

| 方向 | 消息 | 说明 |
|---|---|---|
| 手机 → | `{t:'join', v, session}` | 加入会话 |
| 手机 → | `{t:'send', body}` | 发给电脑 |
| 手机 → | `{t:'ping'}` | 心跳 |
| → 手机 | `{t:'online'}` | 电脑在线 |
| → 手机 | `{t:'waiting'}` | 电脑暂时断线（中转服务保留会话 2 分钟） |
| → 手机 | `{t:'recv', body}` | 电脑发来的消息 |
| → 手机 | `{t:'ended', reason}` | 会话结束：`stopped` / `idle` / `quit` / `desktop-gone`（电脑断线超过 2 分钟） |
| → 手机 | `{t:'not-found'}` | 会话不存在（已结束或链接不对） |
| → 手机 | `{t:'kicked'}` | 被电脑断开（手机满了，或被移除） |
| → 手机 | `{t:'pong'}`、`{t:'error', code}` | 心跳回复；错误 |

`body` 是加密后的内容 `{iv, ct}`（base64url），中转服务原样转发。`phone` 是中转服务分配的 16 字节随机连接号，电脑发来的格式不对就当作坏帧。

关闭码都在 `CLOSE_CODES` 里：`1000` 正常、`1008` 违反协议、`1013` 满了稍后再试、`4000` 心跳超时、`4001` 被同一台电脑的新连接取代、`4002` 连接超时。

### 5.2 内层消息（加密，只有手机和电脑能看到）

| 方向 | 消息 | 说明 |
|---|---|---|
| 手机 → 电脑 | `{type:'hello', token, device}` | 加入或恢复；`device` 是页面从 UA 得出的简短描述，例如「iPhone · 微信」 |
| 手机 → 电脑 | `{type:'submit', nonce, seq, job, raw, force}` | 提交打印任务；`job` 是幂等键，见 4.3 |
| 电脑 → 手机 | `{type:'welcome', token, nonce, printer}` | 加入或恢复成功；`printer` 是当前打印机的显示名，没选时为 null |
| 电脑 → 手机 | `{type:'denied', reason}` | 没被接纳：`full`（手机满了）/ `removed`（被电脑移除）/ `locked`（电脑暂停了新手机加入） |
| 电脑 → 手机 | `{type:'printer', printer}` | 电脑上选的打印机变了 |
| 电脑 → 手机 | `{type:'accepted', job, ahead}` | 回复 `submit`：在排队，前面还有 `ahead` 个任务 |
| 电脑 → 手机 | `{type:'queue', jobs: [{job, ahead}]}` | 队伍往前走了：这部手机所有排队中任务的新位置（1–10 条）；只发给位置变了的手机 |
| 电脑 → 手机 | `{type:'started', job}` | 开始打印 |
| 电脑 → 手机 | `{type:'result', job, result}` | 最终结果：`printed`（带规则名和字段摘要）、`duplicate`、`invalid`、`failed`，或 `no-printer` |
| 电脑 → 手机 | `{type:'refused', job, reason}` | 没有接受（也就没有执行）：`rate-limited` / `too-many-pending` |

### 5.3 心跳与重连

- **心跳**：电脑和手机每 25 秒发一次 `ping`，10 秒内没收到 `pong` 就判定断线，主动关闭连接并重连。
- **连接超时**：发起连接后 10 秒还没连上就放弃这次，按退避重来（弱网下握手偶尔卡住，浏览器自己要等很久才报错）。
- **重连间隔**：依次为 1、2、5、10、30 秒，之后保持 30 秒。**被对端接纳后才从头算起**（电脑收到 `opened`，手机收到 `online` / `waiting`）：只是连上、马上又被中转服务关掉（满了、会话不存在）时继续拉长间隔，不会每秒重连。
- **版本不对**：手机收到 `error: version` 时停止重连，提示刷新页面（页面是 `no-cache` 的，刷新就拿到新版本；发件箱还在，接着发）。
- **反向代理超时**：读超时（nginx 的 `proxy_read_timeout`）设 120 秒，比心跳间隔长得多。
- **电脑断线**：中转服务告诉手机 `waiting`，会话保留 2 分钟。电脑在这段时间内重新 `open` 了，就告诉手机 `online`；否则告诉手机 `ended: desktop-gone` 并忘掉这个会话。
- **中转服务重启**：
  - 内存里的会话全部丢失。电脑和手机各自重连：电脑重新 `open`（`ownerSecret` 不变），手机重新 `join`，再用令牌 `hello`。
  - 手机可能比电脑先连上，这时会收到 `not-found`。从没被接纳过的手机，这就是链接失效；被接纳过的手机（包括刷新页面前被接纳过、存着令牌的）把它当作「电脑还没回来」，顶部提示「电脑暂时断线」，按中转服务保留断线电脑的同一个宽限期（2 分钟）继续重连，过了宽限期才提示链接已失效。两边的等待时间是同一个常量 `DESKTOP_GRACE_MS`。
  - 重连被接纳后，手机把发件箱里的任务原样重发（4.3），中转服务重启期间扫的也不会丢。

## 6. 手机扫码页

### 6.1 页面状态

`连接中 → 取景扫码`，另有「已结束」「链接无效」「没被接纳（手机满了 / 被移除 / 暂停加入）」「页面需要更新」几个终止状态；摄像头不可用时降级为拍照识别和手动输入。

- **取景一直开着**：扫码不会切走画面。每个任务是列表里的一条：`发送中 → 排队中（前面还有 N 张） → 打印中 → 结果`，或者 `被拒绝`。列表保留最近 20 条已结束的任务；还在等结果的一直保留。
- **连接状态单独显示**：断线时顶部出现提示条（「正在重新连接」「电脑暂时断线」），照样可以扫，任务先存在手机上，连上后自动发送。
- **打印机**：顶栏只在扫码时显示电脑选的打印机，连上之前和结束之后不显示。
- **状态机**：状态转换写成纯函数（reducer），用 `bun test` 测试。状态用可辨识联合表示，「有结果却没有结果内容」这类不可能的状态写不出来。
- **控制器**：`phone-controller.ts` 把状态机、会话、摄像头、解码和页面接起来；摄像头、解码器、振动、计时器、页面可见性都经接口注入，用 `bun test` 测试。`main.ts` 只创建真实的浏览器对象。
- **会话结束时收尾**：关掉摄像头、取景循环、解码 worker，不再听页面可见性。
- **无障碍**：任务列表按任务号复用节点，只改变了的条目；最新一张的结果由单独的朗读区（`role="status"`）读出，屏幕阅读器不会把整个列表重读一遍。按钮不小于 48px；橙底、黄底按钮用墨色字，保证对比度。
- **没有链接**：直接打开 `/m/`、没有 `#` 部分时，提示「在电脑上点「手机扫码」，再用手机扫电脑上的二维码」。

### 6.2 扫码

- **解码库**：zxing-wasm 的 reader（ZXing C++ 编译成 WebAssembly）。
  - 放在 Web Worker 里跑，不卡界面。
  - `.wasm` 由中转服务自己提供（`locateFile` 指向本站）。它的默认地址是国外 CDN，在国内不稳定。
  - 为什么不用浏览器自带的 `BarcodeDetector`：iPhone 的 Safari 没有它，而且不同手机上的效果不一致。
- **码制**：QR Code、Data Matrix、Code 128、Code 39、EAN-13、EAN-8、UPC-A。不开 ITF 等容易误识的码制。
- **编码**：码里声明了字符集（ECI）时按声明解码；没声明时按原始字节自己判断，不用 ZXing 的猜测。
  - 原因：短的 GBK 中文可能恰好是合法的 UTF-8，例如「图片色」的 GBK 字节按 UTF-8 解出来是「ͼƬɫ」，「帽」是「ñ」，「路」是「·」。严格的 UTF-8 校验和 ZXing 的猜测都会上当（已实测）。
  - 判断依据：只有 2 字节 UTF-8 字符、按 GBK 读都落在 GB2312 的常用汉字区、GB18030 结果干净，并且（有 Latin-1 以外的字符，或者这些字符都不紧挨英文字母）。「Café」「Müller」「5°C」「60×40」保持原样。
  - 规则见 `relay/web/src/barcode-text.ts`。UTF-8、多行、GBK（含上面这些情况）和拉丁文字都有单元测试。
- **识别组件**：worker 一启动就加载 wasm，加载好了告诉页面；加载时间不算进单帧时限。单帧 5 秒没结果就结束 worker、重开一个；连续卡住，或者 wasm、worker 脚本加载失败，就判定识别组件坏了：关掉摄像头，提示刷新页面，只留手动输入。
- **取景**：
  - 页面上点「开始扫码」才打开摄像头；打不开或被系统中断（别的应用占用、权限被收回）时显示「重新打开摄像头」；
  - 后置摄像头（`facingMode: 'environment'`），理想分辨率 1280×720；
  - 只解码取景框里看得见的那一块（画面按 `object-fit: cover` 裁切显示，看不见的边上可能有别的标签）；
  - 每秒解码约 6 帧，同一时间只有一帧在解码。
- **防抖**（`scan-gate.ts`）：
  - 同一张标签停在镜头里只提交一次；离开画面 1 秒后再扫到，才算新的一次（同款的几件衣服一件件扫，移到下一件通常要一两秒）。换一个码立即生效。
  - 镜头一直看得到同一个码时（一卷内容相同的标签）永远不会放行：最新一张打好后，任务上有一个整行的「再打一张」，点一下打一张。它和「强制补打」一样是明确要打的，不受电脑防重复窗口的限制。
  - 自动扫到的同一个码离开画面 1 秒后放行，但离上次打印不到电脑的防重复窗口（默认 3 秒）时，电脑仍会拦下并提示「强制补打」。
  - 每个码分开记：画面里同时有两张标签、解码轮流读到它们时，两张都只打一次。
  - 拍照识别、手动输入、点「重试」或「强制补打」是用户明确要打的，不经过防抖，但会被记住，免得镜头里的同一张又打一次；也不会让镜头里那一张重新算起。
  - 等结果的任务达到 10 个时暂停提交，并提示稍等；这时镜头里新出现的码不记，等能提交了再扫到就放行。
- **对焦**（`camera-features.ts` 计算约束，`camera.ts` 只调用浏览器 API）：
  - 安卓（Chrome、微信内核）通过 `track.getCapabilities()` 暴露对焦能力。打开摄像头后读取能力：支持 `focusMode: 'continuous'` 就显式设置持续对焦，不依赖厂商默认值（有的机型默认对焦在近距离会糊）。
  - **点按对焦**：点取景画面的某处，把那一点设为对焦点（`pointsOfInterest`）。
    - 画面是 `object-fit: cover` 裁切显示的，点的位置要换算成视频画面里的归一化坐标。
    - 设备只支持单次对焦（`single-shot`）时，就单次对焦到这一点。
    - 点按处显示一个对焦圈。
  - **适度变焦**：很多手机主摄的最近对焦距离在 10 厘米左右，凑太近反而糊。支持 `zoom` 的设备默认放大到 1.5 倍（按设备的步长对齐，不超过上限），拿远一点标签也能充满框，同时在对焦范围内。
  - **切换焦段**：双击取景画面，或点取景框下沿的「焦段」按钮，在近焦（1.5 倍）和远焦（3 倍，超过设备上限就取上限）之间切换，并提示「已切到远焦：离标签远一点扫」。
    - 浏览器拿到的是系统合成的「逻辑摄像头」时，变焦过了长焦镜头的倍数，系统自己换到长焦镜头；没有长焦的手机是数码放大。网页不按镜头名字去选摄像头（名字随系统语言变，也分不出哪个是长焦）。
    - 远焦不比近焦更近（不能变焦、最大倍数不到 1.5 倍以上）时不显示「焦段」按钮，双击也不切换。
    - 切到后台再回来、重新打开摄像头时沿用选好的焦段；设备拒绝切换时焦段不变，按钮照实显示。
    - 单击仍是点按对焦；双击的第二下不对焦，连点三下只切换一次。
  - iPhone（Safari 和微信都是 WebKit）从 Safari 17 起只暴露变焦，对焦由系统持续自动完成，网页无法控制，也不需要控制。
  - 能力不支持或设置失败时安静降级，只记日志，不影响扫码。
- **手电筒**：摄像头支持时（多数安卓 Chrome）显示手电筒开关；设置成功后按钮才改状态。
- **页面不能放大**：双指放大、双击放大都禁掉，放大后取景框和按钮会跑出屏幕，很难缩回来。三层一起做：viewport 的 `user-scalable=no`（Chrome）、页面的 `touch-action: pan-x pan-y`（Chrome 和 Safari），iPhone 的 WebKit 为了无障碍不理会前者，再取消它的 `gesturestart` 事件。输入框字号 16px，iPhone 聚焦时不会自动放大。
- **屏幕常亮**：取景时申请屏幕常亮（Wake Lock），页面隐藏时停掉摄像头，回到页面再打开。打开摄像头期间切到后台，拿到的画面和屏幕常亮都立即放掉。
- **降级**：摄像头被拒绝或不可用时，提供两种方式：
  - 「拍照识别」：`<input type="file" accept="image/*" capture="environment">`；
  - 「手动输入」：一个输入框（关掉自动大写、自动更正、拼写检查）。没提交成功时输入的内容留着。

### 6.3 结果

- **结果文字**：标题用 `VOICE_CUE_TEXT`，和电脑的状态栏、语音播报用同一句话（经 `src/shared/print-cues.ts` 对应），说明文字换成手机上的操作指引。
  - 成功：显示字段摘要，例如「CL5640 · 图片色 · XL」，认得出打的是哪一张。
  - 重复扫码被拦截：说明防重复窗口，带「强制补打」。
  - 打印机故障、没选打印机：带「重试」；打印超时（可能已出纸）只带「强制补打」。
  - 识别不了：说明原因（例如电脑上没有能识别它的规则）。
- **反馈**：
  - 扫到时短振动一下（支持振动的手机上）；打印机故障这类故障级结果（和电脑语音的级别一致）振动两下，无法识别、重复这类提醒级结果不振动；
  - **提示音**：iPhone 的浏览器（Safari、微信）不支持振动，所以同时响声音：扫到码「嘀」一声（2 kHz、70ms，和扫码枪一样），故障级结果两声低音（440 Hz、各 150ms、间隔 100ms），提醒级结果不响。电脑回报「已发送打印」不响：它比「嘀」晚一秒左右，接连两声反而吵。
    - 用 Web Audio 现场合成（振荡器加 5ms 渐入渐出，没有爆音），不下载音频文件；
    - iPhone 只允许在点按里打开声音：「开始扫码」解锁，之后每一次点按都顺带恢复（切到后台再回来会被挂起）；Safari 16.4+ 把音频会话设成 `transient`，只短暂压低正在放的音乐；
    - 取景框左下角有「声音」开关（默认开），记在 `localStorage`；静音开关打开时 iPhone 可能不出声，画面照常提示；
  - 取景框的颜色跟着最新一张的结果变（黄 = 进行中，绿、橙、红 = 结果）。
- **打印机**：页面顶部显示电脑当前选的打印机，电脑上换了会即时更新。

### 7.2 打印

- **执行任务**：`PrintService.submit({ raw, printerName, source: 'mobile', force })`，一个任务执行完再执行下一个。
  - 打印机取设置里当前选中的打印机（`selectedPrinter`，含系统名和显示名）：打印用系统名，告诉手机用界面上的显示名；没选时结果是 `no-printer`，不调用 `PrintService`。
- **会话号被占**（`error: session-taken`，正常不会发生）：换一个新会话，二维码随之更新；新会话马上又被占，说明中转服务不正常，停下来报错（`session-taken`），不来回重试。
  - 成功时回复的字段摘要取自 `PrintService` 返回的识别结果（已经过加工步骤）。
- **打印机变化**：设置里的打印机变了，就给已连接的手机推 `printer`。
- **不依赖界面**：手机的打印由主进程直接执行，不经过界面。
  - 窗口隐藏在托盘时也能打印。
  - 配置中心打开时也能打印：「配置中心里不打印」指的是扫码枪在配置中心里的键盘输入，和手机无关。
- **打印结果通知**：照常发出，来源为 `mobile`。
- **打印机异常**：离线、缺纸等照常弹系统通知。

### 7.3 界面（基于配置中心的新结构）

- **标题栏的「手机扫码」按钮**：放在「配置」和打印机之间，样式和「配置」按钮一致；会话进行中时带一个状态点。
- **浮层**（非模态，不用 `showModal`）：扫码框和 F2 照常可用；按 Esc 关闭，焦点回到扫码框。按状态显示不同内容：
  - 连接中；
  - 二维码和「用手机相机或微信扫一扫，最多 5 部」；还没有手机加入时显示有效期倒计时，过期后可以「重新生成」；
  - 已加入的手机列表：每部显示描述（例如「iPhone · 微信」）、在线与否、已打印张数，带「移除」按钮；
  - 暂停加入时显示「已暂停新手机加入」和「允许新手机加入」；
  - 排队中的任务数、本次已打印张数；
  - 连不上中转服务、没填中转地址、没选打印机：显示原因，带去配置的链接（复用 `PageLink` / `StatusView.link`）。
  - 底部是「结束」按钮。关掉浮层不结束会话，二维码可以再打开给后来的人扫。
- **配置中心「集成」分组的「手机扫码」页**：中转地址（失焦或回车保存）、「恢复默认」、当前状态。
- **二维码**：界面用现有的 `qrcode` 依赖在本机生成（`useQrImage`，和「关于」页的店铺二维码同一个做法），不请求任何在线服务；CSP 已允许 `img-src data:`。
- **浮层只在工作台上显示**：配置中心打开时隐藏；在配置中心里点「手机扫码」先回到工作台（经过未保存修改的确认）。
- **焦点**：浮层标了 `data-keep-focus`，焦点在里面的按钮上时不被拉回扫码框，键盘能操作；扫码枪的字符照样进扫码框。关闭时焦点立即回到扫码框。
- **窄窗口**：1024 宽度下有待安装的更新时，店铺胶囊让位，标题栏不溢出。
- **打印记录**：手机打印的记录来源显示「手机」（`status-text.ts` 已有）。收到手机打印的结果后刷新打印记录。
- **不在电脑上播报手机的打印结果**：拿手机的人可能不在电脑旁，结果显示在手机上；电脑前的操作员正在用扫码枪时，也不该被插话打断。
- **IPC**：
  - `mobile:start`：开始或返回当前会话；
  - `mobile:stop`：结束会话；
  - `mobile:status`：读取当前状态；
  - `mobile:remove-phone`：移除一部手机（参数是状态里的手机 id）；
  - `mobile:set-join-locked`：暂停或重新允许新手机加入；
  - `mobile:status-changed`：主进程推送状态变化。
  - 参数照例经 `ipc-validators.ts` 校验。

### 7.4 中转地址

项目是开源的，代码里不写任何域名。

- **设置项**：新增设置 `mobileRelayUrl`（字符串或 null），在配置中心的「手机扫码」一节里填写，旁边有「恢复默认」。
  - 必须是 `https://` 地址，路径以 `/` 结尾（没有时自动补上）；`http://` 只接受 `localhost` 和 `127.0.0.1`，给开发和测试用。
  - 手机上的摄像头只在 https 页面里可用，所以正式使用只能是 https。
- **默认值**：构建时由环境变量 `CDL_LABELFLASH_DEFAULT_RELAY_URL` 注入（electron-vite 的 `define`）。
  - 官方安装包由 CI 构建，CI 从仓库的 Actions 变量 `LABELFLASH_DEFAULT_RELAY_URL` 读取这个值，指向 yterm.cn 上的官方中转服务；发布作业在变量没设时直接失败。
  - CI 的检查作业不注入：E2E 要验证「没有默认地址」时的提示。
  - 自己构建时不设这个变量，就没有默认值。
  - 界面经 `AppInfo.defaultRelayUrl` 知道默认地址，配置页据此显示「不填就用…」和「恢复默认」。
- **取值顺序**：设置里填了就用设置，否则用默认值；两者都没有时，「手机扫码」按钮提示先去配置中心填写中转地址。
- **换地址**：会话进行中改了地址，先结束当前会话，下次点「手机扫码」时连新地址。

## 8. 部署

任何有域名和 https 证书的服务器都能部署，官方的中转服务部署在 yterm.cn。仓库里只写通用的做法，不写具体服务器的配置。

- **环境变量**：
  - `PUBLIC_ORIGIN`（必填）：扫码页对外的 origin，例如 `https://relay.example.com`；
  - `PORT`：默认 3180；`HOST`：默认 `0.0.0.0`（容器内）。
- **容器 `labelflash-relay`**：
  - 基础镜像 `oven/bun:1.4.2-alpine`，和开发用的 Bun 版本一致；
  - 以非 root 用户运行，文件系统只读；
  - 只绑定 `127.0.0.1:3180`；
  - 内存上限 128 MB；
  - 日志 5 MB × 2 份轮转；
  - `--restart unless-stopped`。
- **反向代理**：在已有 https 站点下加一个路径前缀，例如 `/labelflash/`（nginx 示例见 `relay/deploy/nginx-location.conf`，域名用占位符）：
  - 转发到 `127.0.0.1:3180`，去掉路径前缀；
  - 支持 WebSocket 升级，读超时 120 秒，请求体上限 64k；
  - 传 `X-Real-IP`。
  - 电脑里填的中转地址就是 `https://<域名>/labelflash/`。
- **发布**：`bun run relay:deploy`。目标服务器从环境变量读取，不写进仓库：
  - `RELAY_DEPLOY_SSH`：ssh 主机名；
  - `RELAY_PUBLIC_ORIGIN`：传给容器的 `PUBLIC_ORIGIN`；
  - `RELAY_HEALTH_URL`：对外的健康检查地址。
  - 依次做这几件事：
    1. 本机构建服务端 bundle 和扫码页；
    2. 经 ssh 上传到服务器的 `~/labelflash-relay/<版本>/`；
    3. `docker build`；
    4. 替换容器；
    5. 请求健康检查，确认新版本已在运行；失败时换回上一个镜像。
  - 工作区有没提交的改动（版本号带 `.dirty`）时不发布；服务器上正在运行的就是这个版本时也不发布（同一个标签会覆盖旧镜像，出问题时没有可以换回的版本）。
  - 发布成功后只保留最近两个版本的目录和镜像。
- **健康检查**：`GET /healthz` 返回 `{ ok, version, sessions, connections }`，不含会话号。

## 9. 需要澄清的问题与结论

| 问题 | 结论 |
|---|---|
| 中转地址写在哪？ | 代码里不写。设置项 `mobileRelayUrl`；官方安装包的默认值在构建时注入，见 7.4 |
| 平时要不要连着中转服务？ | 不连。点「手机扫码」才连，会话结束就断 |
| 几个人能同时用吗？ | 能。最多 5 部手机加入同一个会话，任务共用一个队列，先来先打（4.3、4.4） |
| 二维码被拍照外传怎么办？ | 电脑上始终列出已加入的手机，可以移除（令牌作废，同时暂停新手机加入）或结束会话；10 分钟没人加入就作废 |
| 中转服务能看到扫码内容吗？ | 看不到。内容端到端加密，密钥只在二维码的 `#` 部分 |
| 中转服务被攻破，能重放打印请求吗？ | 不能，见 4.3（本次连接的 `nonce` 加严格递增的 `seq`；同一个任务号也只执行一次） |
| 中转服务重启，会话会丢吗？ | 不丢。会话由电脑持有，中转服务不存状态，双方重连后继续；手机上没出结果的任务原样补发 |
| 手机扫到就打，还是确认后打？ | 扫到就打，和扫码枪一样。镜头里的同一张只打一次（6.2 防抖），电脑的防重复窗口是第二道防线 |
| 请求发出去没回音，到底打了没有？ | 协议上不存在这种不确定：任务号是幂等键，手机重发同一个任务号只会拿到已有的进度或结果（4.3） |
| 扫得比打得快怎么办？ | 电脑按顺序排队打印；等结果的超过 10 张时明确拒绝（`too-many-pending`），手机暂停提交并提示 |
| 打到哪台打印机？ | 电脑当前选中的打印机，手机上不能改 |
| 电脑上没选打印机？ | 手机提示「请先选择打印机」，不打印 |
| 窗口隐藏、配置中心打开时？ | 照常打印，见 7.2 |
| 电脑要不要播报手机的打印结果？ | 不播报，结果显示在手机上，见 7.3 |
| 手机识别乱码？ | 有 ECI 按声明；没有时按原始字节判断 UTF-8 还是 GBK，不用解码库的猜测（6.2）。UTF-8、GBK 都有测试 |
| iPhone 微信里摄像头打不开？ | 自动降级为拍照识别或手动输入；是否能实时取景待真机验收 |
| 手机页面的用词和电脑不一致？ | 标题共用 `VOICE_CUE_TEXT`，结果到播报句的对应放在 `src/shared/print-cues.ts` |
| 多家店共用一台中转服务？ | 每台电脑自己的会话互不相干；容量上限见 4.5。也可以各自部署，在设置里填自己的地址 |
| 店里网络需要代理？ | 不支持系统代理，README 写明 |
| 中转服务升级后和旧版电脑不兼容？ | 消息带版本号；版本不支持时回复 `error: version`，电脑提示「请更新软件」。中转服务升级时保持旧版本可用 |
| 中转服务占多少资源？ | 不写磁盘，内存上限 128 MB，日志限 10 MB，适合和其他服务共用一台小服务器 |
| 为什么不用局域网直连？ | 见第 10 节 |

## 10. 取舍

- **云端中转，而不是局域网直连**：
  - 手机网页要实时调用摄像头，浏览器要求页面是 https，而且证书受信任。局域网只能用自签证书，iPhone 和微信里基本用不了。
  - 局域网直连还要处理 Windows 防火墙（放行需要管理员权限）、访客 Wi-Fi 的设备隔离、电脑 IP 变化。
  - 云端中转由电脑主动连出去，这些问题都没有。代价是店里要能上网，偶尔补打的场景可以接受。
- **按需连接，而不是常连**：平时没有连接，服务器负担和暴露面都更小。代价是每次用手机都要到电脑前点一下，偶尔补打可以接受。
- **中转只转发，会话放在电脑上**：服务端没有状态，重启不丢会话，也不需要数据库。
- **端到端加密**：中转服务可能由别人部署，或者和其他服务共用一台服务器；加密后它看不到内容。WebCrypto 在浏览器和 Node 里都有，不增加依赖。
- **扫到就打**：操作和扫码枪一致，最快。误打的风险由两层挡住：页面防抖（同一张停在镜头里只打一次）和电脑的防重复窗口。
- **幂等任务，而不是请求 / 超时**：移动网络随时会断。靠「请求超时就提示用户去看打印机」来兜底，等于把协议的不确定性推给用户。任务号 + 发件箱 + 电脑端去重，让每一张都恰好执行一次，断线、重连、中转服务重启都不影响。代价是电脑要保存每个会话的任务结果（最多 1000 条，内存里）。
- **排队 + 明确拒绝，而不是「忙」**：任务按顺序排队；超出上限时明确拒绝并说明原因（背压），被拒绝的任务一定没有执行，可以放心重交。

## 11. 测试

- **单元测试**（`bun test`）：
  - 协议校验函数：每种消息的合法与非法输入；
  - 加解密往返、附加数据不符时失败、篡改后失败；
  - 结果到播报句的对应；
  - 中转服务的路由核心：登记、接管、加入、转发、踢出、宽限期、限流、容量，用假连接和假时钟；
  - 电脑端的会话状态：加入、手机满了、移除后令牌作废、`nonce` 和 `seq`、共用队列和排队位置、任务去重和结果重放、每部手机的背压、合计限流、到期；
  - 手机端的会话：发件箱、重连后原样重发、确认超时重发、进度查询、页面刷新后恢复、按 `seq` 顺序发出；
  - 手机页面的 reducer、控制器（假摄像头、假解码器）、防抖、结果文字、会话存储；
  - 最坏情况的消息大小：最长的请求和结果都放得进一帧；
  - 解码：用 `qrcode` 生成 UTF-8、多行和 GBK 中文的二维码图片，确认解出原文；GBK 恰好是合法 UTF-8 的情况单独测。
- **集成测试**（`bun test`）：
  - 启动真实的中转服务（随机端口），接上电脑端的 `mobile-host` 和一个脚本手机，走完加入 → 提交 → 排队 → 开始打印 → 结果 → 结束；
  - 再覆盖：两部手机的任务按先后排成一队、各自只收到自己的结果和排队更新（打印由测试放行，位置不取决于打印快慢）；第 6 部手机被拒绝；移除手机后暂停加入、重新允许；同一个任务号重发只打一次；中转服务重启后补发、手机列表对得上。
- **浏览器测试**（Playwright，本机 Edge，假摄像头）：
  - 把含二维码的画面做成 Y4M 视频，作为假摄像头；
  - 打开本机中转服务上的扫码页，确认页面从取景画面里解出内容，并经中转服务送到脚本电脑端。
- **电脑 E2E**（`e2e/mobile.e2e.ts`）：构建中转服务并在本机随机端口启动，Electron 连上去，用扫码页自己的 `PhoneSession` 当手机提交任务，打印记录里出现来源为「手机」的一条；浮层非模态、Esc 后焦点回到扫码框；配置页校验、保存、恢复默认地址。
- **视觉验收**：V32（标题栏按钮和浮层）、V33（配置页），1024×680、1280×800、1920×1080 各截图。
- **真机验收**（记入 `docs/windows-acceptance.md`）：
  - 手机：iPhone Safari、iPhone 微信、安卓 Chrome、安卓微信；
  - 扫码：扫实际打印出来的标签（含中文），在电脑的热敏标签机上出纸；
  - 异常：摄像头被拒后拍照识别；第二部手机被拒绝；结束会话、30 分钟到期；手机断网再恢复；中转服务重启。

## 12. 分阶段

前四个阶段只新增文件，不改 `src/renderer`、`e2e` 和主进程已有的文件；第五个阶段基于配置中心的分支（`feature/config-center`）做，和它一起合回 `feature/phase1-desktop-client`，随 1.0.1 发布。

1. **协议与中转服务**：`src/shared/mobile-protocol.ts`、`mobile-crypto.ts`、`print-cues.ts`，`relay/src/`，以及测试。
2. **扫码页**：`relay/web/`、构建脚本、解码测试。
3. **电脑端模块**：`src/main/mobile/` 里不依赖 Electron 的模块，先不接线；经真实中转服务的集成测试。
4. **部署与浏览器验证**：Docker 镜像、反向代理示例、`relay:deploy`；部署官方中转服务；假摄像头的浏览器测试；把扫码页交给需求方用真手机试。
5. **接入电脑**（基于配置中心的分支）：
   - 主进程接线、IPC、preload、标题栏按钮和浮层、配置中心的「手机扫码」页；
   - 设置项 `mobileRelayUrl`；构建时注入默认地址，CI 从 Actions 变量读取；
   - 界面的 `feedback-cues.ts` 改用 `print-cues.ts`，删掉重复的对应关系；
   - E2E、README 和各级 CLAUDE.md；
   - Windows 和 macOS 验收（含真手机出纸）；官方中转服务部署好，安装包的默认地址能连上；随 1.0.1 发布。
