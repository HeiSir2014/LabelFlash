# 手机扫码打印（云端中转）设计

- 日期：2026-09-29
- 状态：方案已确认（按需连接云端、二维码直接是私有子链接）
- 目标版本：1.1.0（1.0.1 发布之后）
- 取代：总设计第 1 节里 Phase 2 的「主进程内 HTTPS 服务、自签证书、token/PIN 认证」方案，原因见第 10 节

## 1. 目标与范围

**场景**：偶尔补打。扫码枪不在手边，或者在样衣架旁翻到一件要补标签的样衣，用手机摄像头扫它的二维码或条码，标签从店里电脑接的热敏标签机出来。

**做**：

- 电脑上点「手机扫码」，屏幕显示一个二维码；手机用相机或微信扫它，打开扫码页。
- 手机页面实时取景扫码；扫到后显示识别结果，点「打印」才打。
- 电脑按本机的识别规则、加工步骤、模板、防重复窗口打印，和扫码枪扫的完全一样，打印记录的来源记为「手机」。
- 摄像头用不了时，可以拍照识别或手动输入。

**不做**：

- 多部手机同时用一个会话（一个会话只给一部手机）。
- 手机上连续扫码自动打印（每张都要确认）。
- 手机上选打印机、改模板或设置。
- 账号体系；局域网直连；断网时的手机扫码（扫码枪不受影响）。

## 2. 使用流程

1. **开始**：在电脑的工作台点「手机扫码」。这时电脑才连接中转服务，生成一个私有链接，并显示成二维码。
2. **配对**：手机用系统相机或微信扫这个二维码，打开扫码页。第一部打开的手机占用这个会话，之后别的手机再打开会被拒绝。
3. **扫码**：页面打开摄像头。扫到一个码后停止取景，显示识别出的规则、字段和模板。
4. **打印**：点「打印」，电脑打印，结果回到手机上。成功时 1.5 秒后自动继续扫；有问题时停在结果页，等操作员处理。
5. **结束**，出现以下任一情况时，链接作废、电脑断开中转服务：
   - 在电脑上点「结束」；
   - 二维码显示后 10 分钟没有手机打开；
   - 30 分钟没有扫码；
   - 电脑上的程序退出。

## 3. 架构

```
手机浏览器 ──wss──▶ yterm.cn/labelflash/ ──▶ 中转服务（Docker 容器）◀──wss── 电脑主进程 ──▶ PrintService ──▶ 热敏标签机
   扫码页（同一个地址提供）      nginx 终结 TLS            只转发            电脑主动连出去
```

| 部分 | 位置 | 职责 |
|---|---|---|
| 协议 | `src/shared/mobile-protocol.ts` | 两层消息的类型、校验函数、常量；中转服务、手机页面、电脑三方共用 |
| 端到端加密 | `src/shared/mobile-crypto.ts` | AES-256-GCM 加解密消息内容（WebCrypto，浏览器和 Node 都能用） |
| 打印结果用语 | `src/shared/print-cues.ts` | 打印结果 → 播报句（`VOICE_CUE_TEXT`）的对应关系；手机页面和界面共用，用词一致 |
| 中转服务 | `relay/src/` | Bun 服务：提供扫码页的静态文件，按会话转发 WebSocket 消息 |
| 扫码页 | `relay/web/` | 手机网页：摄像头、解码、确认、显示结果 |
| 电脑端 | `src/main/mobile/` | 连接中转服务、认领校验、调用 `PrintService` |
| 电脑界面 | `src/renderer/` | 「手机扫码」按钮和弹窗（配置中心重构合回后再做） |

**原则**：

- **中转服务只转发**：不解析消息内容，不做业务判断，不写磁盘。认领、校验、限流、打印都在电脑上做。中转服务重启后，电脑和手机自动重连，会话照常继续。
- **不改 `core/`**：手机的打印经 `PrintService.preview` / `submit`，来源 `mobile` 早已在 `PRINT_SOURCES` 和数据库的 CHECK 约束里。

## 4. 会话与安全

### 4.1 私有链接

- 电脑开始一次会话时生成三样东西，都用系统随机数：
  - 会话号 `sessionId`：16 字节；
  - 所有权密钥 `ownerSecret`：16 字节，只在电脑和中转服务之间用；
  - 内容密钥 `key`：32 字节。
- 链接是 `https://yterm.cn/labelflash/m/#<sessionId>.<key>`，都用 base64url 编码。
- 会话号和内容密钥放在 `#` 后面：浏览器不会把 `#` 后面的部分发给服务器，所以不会出现在 nginx 日志和 Referer 里。

### 4.2 端到端加密

- 手机和电脑之间的应用消息用 AES-256-GCM 加密：
  - 每条消息用新的 12 字节随机 IV；
  - 附加数据是 `labelflash/1/<方向>/<sessionId>`，方向为 `p2d` 或 `d2p`，防止把一个方向的消息反射回去。
- 中转服务只看得到外层信封（会话号、连接号、消息大小和时间），看不到扫码内容、字段、令牌和打印结果。
- 解密失败的消息直接丢弃，写一条日志。

### 4.3 认领与防重放

- **认领**：
  - 手机连上后发 `hello`，带上本地保存的令牌；第一次没有令牌。
  - 会话还没被占用时，电脑认领这部手机：生成 16 字节的令牌，在 `welcome` 里发回。手机把令牌存在 `localStorage`，键名带会话号。
  - 之后同一部手机重连或刷新页面，都带这个令牌。电脑按常数时间比较令牌，一致就放行。
  - 其他手机没有令牌或令牌不对：电脑回复 `rejected`，并让中转服务断开这个连接。
- **防重放**：
  - `welcome` 里带一个本次连接的随机数 `nonce`。
  - 手机之后的每个请求都带上这个 `nonce`，以及在本次连接内递增的 `id`。
  - 电脑拒绝 `nonce` 不对、或 `id` 不大于上一条的请求。
  - 这样即使中转服务被攻破，旧消息也重放不了：重放的旧请求带的是旧 `nonce`；重放 `hello` 得到的 `welcome` 又是加密的，拿不到新的 `nonce`。
- **认领前**：电脑忽略所有 `preview` / `print` 请求。

### 4.4 电脑端的校验和限制

- **不信任手机消息**：每条都按协议的校验函数检查字段和类型。扫码内容再经过 `PrintService` 的规范化（1–1000 字符、没有控制字符）。
- **只能打印**：手机只能请求「预览」和「打印（可选强制补打）」，不能指定打印机、模板或任何设置。
- **限流**：
  - 同一时间只处理一个请求，多的回复 `busy`；
  - 每分钟最多 30 次打印，超出回复 `rate-limited`。
- **发回的内容有上限**：预览结果最多 30 个字段，每个值最多 300 字符，超出截断并标注。

### 4.5 中转服务的防滥用

- **连接**：
  - 只接受 JSON 文本帧，单帧最大 64 KiB；
  - 连接后 10 秒内必须发出第一帧（`open` / `join`），否则断开。
- **频率**：每个连接按令牌桶限速，手机每秒 5 帧（突发 20），电脑每秒 50 帧（突发 100）。超出的帧丢弃并回复错误；累计超出 50 次就断开。
- **容量**：
  - 最多 500 个会话、2000 个连接；
  - 每个会话最多 3 个手机连接；
  - 每个来源 IP 最多 20 个连接。来源 IP 取 nginx 传来的 `X-Real-IP`；服务只监听 127.0.0.1，外面访问不到。
- **来源检查**：手机连接的 `Origin` 必须是 `https://yterm.cn`。
- **所有权**：
  - 会话号第一次 `open` 时，中转服务记下 `ownerSecret` 的 SHA-256。
  - 电脑断线重连时用同一个 `ownerSecret` 再 `open`，中转服务就接管会话，并关掉旧连接。这样处理了半开连接：旧连接其实已经断了，服务端还没发现。
  - `ownerSecret` 不同的 `open` 回复 `session-taken`。
- **日志**：只记连接事件，不记消息内容，会话号只记前 6 个字符。

- **显示内容**：页面只用 `textContent` 显示内容，不用 `innerHTML`。

## 5. 协议

所有消息都是 JSON 文本帧，版本号 `MOBILE_PROTOCOL_VERSION = 1`。

### 5.1 外层信封（中转服务能看到）

电脑 ↔ 中转服务，路径 `/ws/desktop`：

| 方向 | 消息 | 说明 |
|---|---|---|
| 电脑 → | `{t:'open', v, session, secret}` | 登记或接管会话 |
| 电脑 → | `{t:'send', phone, body}` | 发给某个手机连接 |
| 电脑 → | `{t:'kick', phone}` | 断开某个手机连接 |
| 电脑 → | `{t:'close', reason}` | 结束会话，`reason` 为 `stopped` / `idle` / `quit` |
| 电脑 → | `{t:'ping'}` | 心跳 |
| → 电脑 | `{t:'opened'}` | 登记成功 |
| → 电脑 | `{t:'joined', phone}`、`{t:'left', phone}` | 手机连接加入、离开；`phone` 是中转服务分配的连接号 |
| → 电脑 | `{t:'recv', phone, body}` | 手机发来的消息 |
| → 电脑 | `{t:'pong'}` | 心跳回复 |
| → 电脑 | `{t:'error', code}` | `version` / `session-taken` / `bad-frame` / `rate-limited` / `server-busy` |

手机 ↔ 中转服务，路径 `/ws/phone`：

| 方向 | 消息 | 说明 |
|---|---|---|
| 手机 → | `{t:'join', v, session}` | 加入会话 |
| 手机 → | `{t:'send', body}` | 发给电脑 |
| 手机 → | `{t:'ping'}` | 心跳 |
| → 手机 | `{t:'online'}` | 电脑在线 |
| → 手机 | `{t:'waiting'}` | 电脑暂时断线（中转服务保留会话 2 分钟） |
| → 手机 | `{t:'recv', body}` | 电脑发来的消息 |
| → 手机 | `{t:'ended', reason}` | 会话结束：`stopped` / `idle` / `quit` / `desktop-gone`（电脑断线超过 2 分钟） |
| → 手机 | `{t:'not-found'}` | 会话不存在（已结束或链接不对） |
| → 手机 | `{t:'kicked'}` | 被电脑断开（会话已被别的手机占用） |
| → 手机 | `{t:'pong'}`、`{t:'error', code}` | 心跳回复；错误 |

`body` 是加密后的内容 `{iv, ct}`（base64url），中转服务原样转发。

### 5.2 内层消息（加密，只有手机和电脑能看到）

| 方向 | 消息 | 说明 |
|---|---|---|
| 手机 → 电脑 | `{type:'hello', token, device}` | 认领或恢复；`device` 是页面从 UA 得出的简短描述，例如「iPhone · 微信」 |
| 手机 → 电脑 | `{type:'preview', nonce, id, raw}` | 预览：识别、加工、选模板，不打印 |
| 手机 → 电脑 | `{type:'print', nonce, id, raw, force}` | 打印 |
| 电脑 → 手机 | `{type:'welcome', token, nonce, printer}` | 认领成功或恢复；`printer` 是当前打印机的显示名，没选时为 null |
| 电脑 → 手机 | `{type:'rejected'}` | 会话已被别的手机占用 |
| 电脑 → 手机 | `{type:'preview', id, result}` | 结果为 `ok`（规则名、模板名、字段、最近打印、查询失败原因）或 `invalid` |
| 电脑 → 手机 | `{type:'print', id, result}` | 结果为 `PrintResult` 的精简版（不含 `scan`），或 `no-printer` |
| 电脑 → 手机 | `{type:'busy', id}`、`{type:'rate-limited', id}` | 上一个请求还没完成；打印太频繁 |

### 5.3 心跳与重连

- **心跳**：电脑和手机每 25 秒发一次 `ping`，10 秒内没收到 `pong` 就判定断线，主动关闭连接并重连。
- **重连间隔**：依次为 1、2、5、10、30 秒，之后保持 30 秒。
- **nginx 超时**：`proxy_read_timeout` 设 120 秒，比心跳间隔长得多。
- **电脑断线**：中转服务告诉手机 `waiting`，会话保留 2 分钟。电脑在这段时间内重新 `open` 了，就告诉手机 `online`；否则告诉手机 `ended: desktop-gone` 并忘掉这个会话。
- **中转服务重启**：
  - 内存里的会话全部丢失。电脑和手机各自重连：电脑重新 `open`（`ownerSecret` 不变），手机重新 `join`，再用令牌 `hello`。
  - 手机可能比电脑先连上，这时会收到 `not-found`。如果手机曾经被接纳过，就在 30 秒内按重连间隔继续重试，30 秒后才提示链接已失效。

## 6. 手机扫码页

### 6.1 页面状态

`连接中 → 等待电脑 → 取景扫码 → 识别中 → 确认 → 打印中 → 结果 → 取景扫码`，另有「已结束」「链接无效」「已被别的手机占用」「摄像头不可用」四个终止或降级状态。

- **状态机**：状态转换写成纯函数（reducer），用 `bun test` 测试。页面代码只负责渲染和调用浏览器 API。
- **没有链接**：直接打开 `/m/`、没有 `#` 部分时，提示「在电脑上点「手机扫码」，再用手机扫电脑上的二维码」。

### 6.2 扫码

- **解码库**：zxing-wasm 的 reader（ZXing C++ 编译成 WebAssembly）。
  - 放在 Web Worker 里跑，不卡界面。
  - `.wasm` 由我们自己的服务器提供（`locateFile` 指向本站）。它的默认地址是国外 CDN，在国内不稳定。
  - 为什么不用浏览器自带的 `BarcodeDetector`：iPhone 的 Safari 没有它，而且不同手机上的效果不一致。
- **码制**：QR Code、Data Matrix、Code 128、Code 39、EAN-13、EAN-8、UPC-A。不开 ITF 等容易误识的码制。
- **编码**：`textMode: 'Plain'`，按码里的 ECI 或自动猜测的字符集转成文字。UTF-8 和 GBK 编码的中文都要能正确还原，由单元测试覆盖。
- **取景**：
  - 后置摄像头（`facingMode: 'environment'`），理想分辨率 1280×720；
  - 每秒解码约 6 帧，同一时间只有一帧在解码；
  - 扫到一个码就停止取景，进入确认。所以同一个码不会连续提交。
- **手电筒**：摄像头支持时（多数安卓 Chrome）显示手电筒开关。
- **屏幕常亮**：取景时申请屏幕常亮（Wake Lock），页面隐藏时停掉摄像头，回到页面再打开。
- **降级**：摄像头被拒绝或不可用时，提供两种方式：
  - 「拍照识别」：`<input type="file" accept="image/*" capture="environment">`；
  - 「手动输入」：一个输入框。

### 6.3 确认与结果

- **确认卡片**：显示规则名、模板名和字段（名称：值）。
  - 防重复窗口内已经打印过：提示「N 秒内已打印过」，按钮换成「强制补打」。
  - 设为「拦下不打印」的查询失败了：显示原因，不提供打印按钮。
  - 识别不了：显示原因和「重扫」。
- **结果文字**：标题用 `VOICE_CUE_TEXT`，和电脑的状态栏、语音播报用同一句话（经 `src/shared/print-cues.ts` 对应），说明文字换成手机上的操作指引。
- **反馈**：
  - 成功时短振动（支持振动的手机上），1.5 秒后自动回到取景；
  - 提醒和故障停在结果页，等操作员点「继续扫码」或「重试」。
- **打印机**：页面顶部显示当前打印机的名称。

## 7. 电脑端

### 7.1 模块（`src/main/mobile/`）

| 文件 | 作用 | 依赖 Electron |
|---|---|---|
| `relay-endpoint.ts` | 中转地址：默认 `https://yterm.cn/labelflash/`；开发版可以用环境变量 `CDL_LABELFLASH_RELAY_URL` 改成本机的中转服务（安装版忽略） | 否 |
| `relay-link.ts` | WebSocket 连接：心跳、重连、所有权；WebSocket 和计时器都由参数注入 | 否 |
| `mobile-session.ts` | 会话状态：认领、令牌、`nonce` 和 `id` 检查、10 分钟 / 30 分钟到期、限流；时间由 `Clock` 注入 | 否 |
| `mobile-replies.ts` | 把 `PrintService` 的结果换成发给手机的精简结果（截断字段，去掉内部信息） | 否 |
| `mobile-station.ts` | 接线：收到请求 → `PrintService`；状态变化推给界面 | 是（只做接线） |

- **WebSocket**：用 Electron 44 主进程自带的全局 `WebSocket`（Node 24），不新增依赖。
- **系统代理**：Node 的 WebSocket 不走系统代理设置。店里的网络要能直接访问 `yterm.cn:443`，这一点写进 README。

### 7.2 打印

- **预览**：`PrintService.preview(raw)`，模板名由 `resolveTemplate` 得出，和工作台一样。
- **打印**：`PrintService.submit({ raw, printerName, source: 'mobile', force })`。
  - 打印机取设置里当前选中的打印机（`selectedPrinter`）；没选时回复 `no-printer`，不调用 `PrintService`。
- **不依赖界面**：手机的打印由主进程直接执行，不经过界面。
  - 窗口隐藏在托盘时也能打印。
  - 配置中心打开时也能打印：「配置中心里不打印」指的是扫码枪在配置中心里的键盘输入，和手机无关。
- **打印结果通知**：照常发出，来源为 `mobile`。
- **打印机异常**：离线、缺纸等照常弹系统通知。

### 7.3 界面（配置中心重构合回后做）

- **工作台标题栏的「手机扫码」按钮**：会话进行中时带一个状态点。
- **弹窗**，按状态显示不同内容：
  - 连接中；
  - 二维码和「用手机相机或微信扫一扫」「10 分钟内有效」；
  - 已连接：显示手机描述、本次已打印张数、最近一张的结果；
  - 手机已断开；
  - 连不上中转服务：显示原因和「重试」。
  - 弹窗底部是「结束」按钮。关掉弹窗不结束会话。
- **二维码**：由主进程用现有的 `qrcode` 依赖生成 SVG，界面按 data URL 显示（CSP 已允许 `img-src data:`）。
- **打印记录**：手机打印的记录来源显示「手机」（`status-text.ts` 已有）。收到手机打印的结果后刷新打印记录。
- **不在电脑上播报手机的打印结果**：拿手机的人可能不在电脑旁，结果显示在手机上；电脑前的操作员正在用扫码枪时，也不该被插话打断。
- **IPC**：
  - `mobile:start`：开始或返回当前会话；
  - `mobile:stop`：结束会话；
  - `mobile:status`：读取当前状态；
  - `mobile:status-changed`：主进程推送状态变化。
  - 参数照例经 `ipc-validators.ts` 校验。

## 8. 部署

- **服务器**：`yterm.cn`（Ubuntu 24.04，2 核，内存 1.9G）。nginx 以 host 网络模式跑在 Docker 里；443 端口按 SNI 分流，`yterm.cn` 的 TLS 站点监听 8443 和 8444（proxy_protocol）。
- **容器 `labelflash-relay`**：
  - 基础镜像 `oven/bun:1.4.2-alpine`，服务器上已有，层共享，几乎不占额外磁盘；
  - 以非 root 用户运行，文件系统只读；
  - 只绑定 `127.0.0.1:3180`；
  - 内存上限 128 MB；
  - 日志 5 MB × 2 份轮转；
  - `--restart unless-stopped`。
- **目录**：服务器上的 `~/labelflash-relay/`，放构建产物和 Dockerfile。
- **nginx**：在 `yterm.cn` 的 TLS 站点里加 `location /labelflash/`（见 `relay/deploy/nginx-location.conf`）：
  - 转发到 `127.0.0.1:3180`，去掉路径前缀；
  - 支持 WebSocket 升级，`proxy_read_timeout 120s`，请求体上限 64k。
  - 只需改一次：先备份配置，`nginx -t` 通过后再 reload。
- **发布**：`bun run relay:deploy`，依次做这几件事：
  1. 本机构建服务端 bundle 和扫码页；
  2. 上传到服务器；
  3. `docker build`；
  4. 替换容器；
  5. 请求 `/labelflash/healthz`，确认新版本已在运行。
- **健康检查**：`GET /healthz` 返回 `{ ok, version, sessions, connections }`，不含会话号。

## 9. 需要澄清的问题与结论

| 问题 | 结论 |
|---|---|
| 平时要不要连着中转服务？ | 不连。点「手机扫码」才连，会话结束就断 |
| 二维码被拍照外传怎么办？ | 一个会话只给第一部手机；10 分钟没人打开就作废；电脑上随时能结束 |
| 中转服务能看到扫码内容吗？ | 看不到。内容端到端加密，密钥只在二维码的 `#` 部分 |
| 中转服务被攻破，能重放打印请求吗？ | 不能，见 4.3（本次连接的 `nonce` 加递增 `id`） |
| 中转服务重启，会话会丢吗？ | 不丢。会话由电脑持有，中转服务不存状态，双方重连后继续 |
| 手机扫到就打，还是确认后打？ | 确认后打。实时取景容易扫到旁边的码，偶尔补打不在乎多点一下 |
| 打到哪台打印机？ | 电脑当前选中的打印机，手机上不能改 |
| 电脑上没选打印机？ | 手机提示「请先选择打印机」，不打印 |
| 窗口隐藏、配置中心打开时？ | 照常打印，见 7.2 |
| 电脑要不要播报手机的打印结果？ | 不播报，结果显示在手机上，见 7.3 |
| 手机识别乱码？ | 解码库按 ECI 或自动识别字符集，UTF-8 和 GBK 都有测试 |
| iPhone 微信里摄像头打不开？ | 自动降级为拍照识别或手动输入；是否能实时取景待真机验收 |
| 手机页面的用词和电脑不一致？ | 标题共用 `VOICE_CUE_TEXT`，结果到播报句的对应放在 `src/shared/print-cues.ts` |
| 多家店共用一台中转服务？ | 每台电脑自己的会话互不相干；容量上限见 4.5 |
| 店里网络需要代理？ | 不支持系统代理，README 写明 |
| 中转服务升级后和旧版电脑不兼容？ | 消息带版本号；版本不支持时回复 `error: version`，电脑提示「请更新软件」。中转服务升级时保持旧版本可用 |
| 服务器磁盘只剩 3.4G？ | 复用已有的基础镜像，日志限 10 MB，不写磁盘 |
| 为什么不用局域网直连？ | 见第 10 节 |

## 10. 取舍

- **云端中转，而不是局域网直连**：
  - 手机网页要实时调用摄像头，浏览器要求页面是 https，而且证书受信任。局域网只能用自签证书，iPhone 和微信里基本用不了。
  - 局域网直连还要处理 Windows 防火墙（放行需要管理员权限）、访客 Wi-Fi 的设备隔离、电脑 IP 变化。
  - 云端中转由电脑主动连出去，这些问题都没有。代价是店里要能上网，偶尔补打的场景可以接受。
- **按需连接，而不是常连**：平时没有连接，服务器负担和暴露面都更小。代价是每次用手机都要到电脑前点一下，偶尔补打可以接受。
- **中转只转发，会话放在电脑上**：服务端没有状态，重启不丢会话，也不需要数据库。
- **端到端加密**：服务器和其他服务共用，加密后服务器看不到内容。WebCrypto 在浏览器和 Node 里都有，不增加依赖。
- **每张确认**：比「扫到就打」多点一下，但不会误打。以后需要连续扫码时，可以加一个「连续模式」开关，协议不用改。

## 11. 测试

- **单元测试**（`bun test`）：
  - 协议校验函数：每种消息的合法与非法输入；
  - 加解密往返、附加数据不符时失败、篡改后失败；
  - 结果到播报句的对应；
  - 中转服务的路由核心：登记、接管、加入、转发、踢出、宽限期、限流、容量，用假连接和假时钟；
  - 电脑端的会话状态：认领、令牌、`nonce` 和 `id`、到期、限流；
  - 手机页面的 reducer；
  - 解码：用 `qrcode` 生成 UTF-8 和 GBK 中文的二维码图片，确认 zxing-wasm 解出原文。
- **集成测试**（`bun test`）：
  - 启动真实的中转服务（随机端口），接上电脑端的 `relay-link` + 会话和一个脚本手机，走完认领 → 预览 → 打印 → 结束；
  - 再覆盖中转服务重启、电脑断线宽限期、第二部手机被拒绝。
- **浏览器测试**（Playwright，本机 Edge，假摄像头）：
  - 把含二维码的画面做成 Y4M 视频，作为假摄像头；
  - 打开本机中转服务上的扫码页，确认页面从取景画面里解出内容，并经中转服务送到脚本电脑端。
- **电脑 E2E**（配置中心重构合回后）：Electron 连本机中转服务，脚本手机扫码后，打印记录里出现来源为「手机」的一条。
- **真机验收**（记入 `docs/windows-acceptance.md`）：
  - 手机：iPhone Safari、iPhone 微信、安卓 Chrome、安卓微信；
  - 扫码：扫实际打印出来的标签（含中文），在电脑的热敏标签机上出纸；
  - 异常：摄像头被拒后拍照识别；第二部手机被拒绝；结束会话、30 分钟到期；手机断网再恢复；中转服务重启。

## 12. 分阶段

配置中心重构合回之前，不改 `src/renderer`、`e2e` 和主进程已有的文件。所以前四个阶段只新增文件，第五个阶段在重构合回后做。

   - E2E、README 和各级 CLAUDE.md；
   - Windows 和 macOS 验收，发布 1.1.0。
