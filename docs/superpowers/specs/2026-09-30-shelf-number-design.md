# 货架号识别（手机扫码 + 本地 OCR）设计

日期：2026-09-30。子项目「货架号识别」的第二部分：把第一部分的本地 OCR 引擎（`docs/superpowers/specs/2026-09-30-ocr-engine-design.md`）接进程序。手机扫到标签上的二维码时，顺带把整张标签拍下来（按二维码摆正）；电脑用 OCR 读出上面的货架号（例如 `A-1-2-3`、`B-12-3-10`），作为一个字段补进这一张再打印。

## 1. 需求方定下的

- 货架号是一个普通字段（键值），和识别规则拆出的「编码」「颜色」同等对待；模板里怎么显示、放在哪，和其他字段一样。
- 识别方式要通用：按正则和「以二维码为基准的相对区域」挑出来，不写死货架号的格式。货架号的每一段可能是两位数。
- **货架号的位置变了也要认得出**：不能依赖它固定印在某个地方。
- 识别不到时，由这一步的设置决定：默认**不打印**，手机上提示「重扫，或手动输入」；也可以设成照常打印、字段留空。
- 识别出来就直接打印，手机上不再确认（结果里显示读出的货架号，认错了可以在电脑上重打）。

## 2. 整体

```
手机扫码页：解码出二维码 → 按二维码四个角摆正 → 截下整张标签（JPEG）→ 随 submit 发出
   ↓ 端到端加密，经中转服务
电脑：submit 带着图 → PrintService.submit({ raw, image, manualFields })
   → 识别规则拆字段 → 加工步骤依次执行
       「图中文字识别」步骤：JPEG → BGRA（Electron nativeImage）→ OCR 读出整张标签的所有文字 → 正则（优先区域先看）→ 字段「货架号」
   → 模板 → 打印
```

- **按二维码摆正**：二维码由本程序打印，和标签同一个方向。手机按二维码的四个角做透视变换，截出来的图里标签总是正的，不管手机横着、斜着拍。区域用「二维码边长」做单位、以二维码左上角为原点描述，和拍摄的远近无关。
- **不依赖固定位置**：手机截整张标签（以二维码为中心，左右上下各留出几个二维码边长），OCR 读出上面的所有文字，按正则找。设置里的区域只决定**先看哪里**：那里没有匹配，就接着找标签的其他地方，货架号换了位置照样认得出；同一张标签上有两处都像货架号时，区域里的优先。
- **电脑决定截多大**：`welcome` 里告诉手机要不要截图、截哪块（默认整张标签：二维码边长的 −2.5 到 3.5 倍、−1.5 到 2.5 倍）、每个二维码边长多少像素（默认 130，货架号的字约有 16 像素高）。以后调整只改电脑，不用更新手机页面。
- 没有图的扫码（扫码枪、本机接口、老的手机页面、「试一试」）：这一步跳过，字段留空，行为和现在一样。

## 3. 加工步骤「图中文字识别」

```ts
interface ImageTextStep {
  kind: 'imageText';
  output: string;          // 字段名，默认「货架号」
  pattern: string;         // 正则，默认 \b[A-Z]{1,2}-\d{1,3}-\d{1,3}-\d{1,3}\b
  flags: string;
  preferredArea: CodeRelativeArea | null;  // 优先查找的区域（以二维码为基准）；null = 不分先后
  whenMissing: 'block' | 'empty'; // 识别不到：不打印（默认）/ 照常打印、留空
}
```

- **优先区域**：预设「不分先后」（默认）、二维码下方（`left −0.1, top 1, right 1.1, bottom 1.6`）、上方、左侧、右侧，也可以自己填四个数。只影响先后，不排除别处。中心落在二维码本身上的文字一律不算（那是把码当成了字）。
- **匹配**：OCR 读出的每段文字先规整（全角转半角，各种横线统一成 `-`，去掉连字符两边的空格）；先在优先区域里、再在其他地方，各按阅读顺序找第一段能匹配正则的，取匹配到的部分。默认正则两边是词边界，不会从 `XA-1-2-3456` 这样的长串里截出半段。正则经主进程的隔离环境执行（有超时），和其他规则一样。字母数字的混淆（O/0、A/4）不猜。
- **手动输入的值优先**：手机上手动补的货架号随重发的请求带过来，这一步直接用它，不再识别。
- **识别不到**：`block` 时不打印，记录失败原因「没认出」（新增的失败原因 `TEXT_NOT_FOUND`，说明写「没认出货架号」）；手机上显示输入框。`empty` 时照常打印，字段不写。
- **OCR 不可用**（macOS 还没有打包 OCR、文件缺失）：电脑不向手机要图，这一步跳过；配置中心的这一步上写明「这台电脑上没有文字识别」。
- 同一次扫码有几个「图中文字识别」步骤时，OCR 只跑一次。

## 4. 协议（手机、中转服务、电脑共用 `src/shared/mobile-protocol.ts`）

都是可选字段，老版本忽略它们，不升协议版本号：

| 消息 | 新增 | 说明 |
|---|---|---|
| `welcome` | `image?: { area, pixelsPerCode }` | 电脑要图时才有。老手机页面忽略它，不截图 |
| `submit` | `image?: { jpeg, code }` | `jpeg` 是 base64；`code` 是二维码在截图里的位置（左上角和边长，像素）。只在 `welcome` 要图时发 |
| `submit` | `fields?: { 字段名: 值 }` | 手机上手动输入的字段（目前只用于补货架号），最多 10 个 |
| `result`（failed） | `field?: string` | 原因是 `TEXT_NOT_FOUND` 时，没认出的字段名；手机据此显示输入框 |

- **大小**：整张标签按每个二维码边长 130 像素截，约 780×520，JPEG 几十 KB。单条消息明文上限从 32 KB 提到 128 KB，单帧从 64 KB 提到 192 KB（中转服务的 `maxPayloadLength` 用同一个常量）。图最多 64 KB，手机按这个上限从高到低试 JPEG 质量。
- **兼容**：老电脑不在 `welcome` 里要图，新手机页面就不截图、帧也不会变大；新电脑遇到老手机页面收不到图，这一步跳过。新的失败原因只会发给新手机页面：**先部署中转服务（带新的扫码页），再发电脑端的新版本**。
- **重发**：待发送的任务连同图存在手机本地（最多 10 个待发），刷新页面、断线重连后重发的还带着图。

## 5. 电脑端

- `PrintRequest` 增加 `image?: ScanImage`、`manualFields?: Record<string, string>`；`PrintService` 把它们交给加工步骤（`enrich(scan, context)`）。
- `EnrichDeps.readImageText(image) → ImageTextRegion[]`：主进程实现（`src/main/ocr/`），JPEG 用 `nativeImage` 解成 BGRA，交给 OCR 引擎。引擎在第一次用到时创建，之后复用；创建失败记日志，这一步按「OCR 不可用」处理。
- 失败原因 `TEXT_NOT_FOUND`：第 5 条迁移重建 `jobs` 表加上这个取值（和第 3 条一样：建新表、复制、删旧表、改名，序号不变）。界面：「没认出货架号，没有打印」（说明里写字段名）；手机扫码的结果照旧不播报；本机接口永远不带图，映射成 `PRINT_ERROR` 只为穷尽。
- 语音新增一句 `textNotFound`：「没认出标签上的字，没有打印」（桌面上用不到，手机结果的标题用它）。

## 6. 手机端（`relay/web/src/`）

- 解码的 worker 把 zxing 的四个角点一起送回来；控制器在同一帧画布上按角点截图（画布在下一次取帧前不变）。
- 截图：输出宽 = 区域宽 × `pixelsPerCode`，高同理，最多 1024×1024；按目标像素反算原图坐标（透视变换，双线性取样），超出画面的部分填白。标签没拍全时，拍到的部分照样识别。
- `result` 是 `TEXT_NOT_FOUND` 时：结果卡片上写「没认出货架号」，下面一个输入框（字号 ≥ 16px）和「打印」按钮；提交后作为新任务重发，带上 `fields`（不带图，也不用再识别）。按钮有声音和震动反馈。

## 7. 打包（Windows）

- 安装包带上 OCR：`resources/ocr/ocr-addon.node`、模型 `models/small/{det.onnx, rec.onnx, dict.txt}` 和 ONNX Runtime 的许可声明。
- 扩展只依赖系统 DLL：ONNX Runtime 由 `scripts/ocr/build-onnxruntime.ts` 从微软的源码编成 /MT 静态库（静态 C 运行库），扩展也用 crt-static 编。
  - 最初用 ort 下载的预编译包：它只有 /MD 版本，扩展因此依赖 VC++ 运行库（要随包带 4 个 DLL），还导入 DirectML.dll；而且它按 `/arch:AVX2` 编，没有 AVX2 的 CPU 上加载就崩。
  - 自己编的按 x64 基线，矩阵运算在运行时挑 AVX2 / AVX-512；二维码附近一块慢约 50 毫秒（0.20 秒对 0.15 秒），换来任何 x64 CPU 都能用。
- 构建：`dist:win` 里由 `scripts/ocr/stage-resources.ts` 下载模型、下载预编译的 ONNX Runtime 静态库、编扩展、核对依赖、用样张识别一次，放到 `dist/.ocr`。
- ONNX Runtime 的静态库只在版本或编译选项变了时编一次：推送 `onnxruntime-v<版本>-<指纹>` 标签，`.github/workflows/onnxruntime.yml` 在 windows-2022 上从源码编（约 50 分钟）、附上构建来源证明，发布成预发布版本（不标成 latest，自动更新看不到它）；代码里记着每个文件的 SHA-256。扩展是我们自己的 Rust 代码，每次打包都从源码编，不做成预编译包：这样标签里的源码和装进安装包的二进制不会对不上。
- macOS：这一版不带 OCR，这一步按「OCR 不可用」处理。

## 8. 测试与验收

- **单元测试**：文字规整、查找先后（优先区域、货架号换了位置、两处都像）、正则匹配（已写：`src/core/scan/image-text.test.ts`）；步骤的校验和执行（有图、没图、手动值、识别不到的两种处理、OCR 不可用、只跑一次 OCR）；协议新字段的解析和兼容（老消息、超长、非法值）；手机端截图的坐标换算、JPEG 大小上限、结果卡片和输入框；迁移 5（旧记录一条不丢）。
- **E2E**：假 OCR（环境变量 `CDL_LABELFLASH_FAKE_OCR`，和假打印机一样只对未打包的程序生效）；测试手机带图提交，打出的标签里有货架号；识别不到时不打印、手机收到 `TEXT_NOT_FOUND` 和字段名，手动补上后打印。
- **扫码页浏览器测试**（`test:relay-browser`）：假摄像头的画面里二维码下面印一行货架号，电脑要图时手机截图发出。
- **真实 OCR**：主进程里加载扩展、识别样张（和第一部分的样张同一张）。
- **人工**：真手机扫真标签（横着、斜着拍），货架号读对；识别不到时手动输入。记进 `docs/windows-acceptance.md`。

## 10. 识别精度评估与模型档位（2026-09-30）

样张是一张清楚的照片，真实扫码是视频帧，所以做了一个模拟评估（`bun run ocr:eval`，`scripts/ocr/eval-shelf-number.ts`）：
按 203 dpi 渲染 60×40 毫米的标签（货架号随机，放在二维码下方、右侧或最底行），模拟手机拍摄（任意角度、倾斜、二维码在画面里的大小、对焦模糊、光线不匀、噪点、视频压缩），
再走程序里真实的代码：扫码页的 `cropLabel` 截图、JPEG 不超过 64 KB、电脑端 OCR 和 `findImageText`。固定随机种子；每个模型组合在单独的进程里跑，内存各算各的。
「读错」（读出一个不对的货架号）单独统计：它比「没找到」危险，没找到时手机会提示重扫或手动输入，读错会直接打出错的标签。

**取图比模型要紧**（small + small，300 张，常规条件）：

| 取图 | 读对 |
|---|---|
| 1280×720 取帧（原来） | 93.0% |
| 1080p 原尺寸截图（现在） | 96.3% |
| 再加上整张标签都在画面里（拍得太近时退远一点） | 98.0% |

读错的样本几乎都是图里本来就没有足够的信息：离得远时字只有十来个像素高，加上模糊，字母被读成数字（QX→Q1、LL→U1）；离得太近时标签的一部分出了画面，货架号被截掉。
所以扫码页改为 1080p，截图用同一时刻整个画面的原尺寸快照（解码照样缩到 1280 以内，速度不变）。
「等整张标签进画面再发」没有做：截图区域（二维码边长的 6×4 倍）比真实标签（约 2.9×1.9 倍）大得多，拿它判断会逼用户离得太远；以后由电脑按模板算出标签的实际范围、发给手机，再做这一步。

**模型对比**（1080p 取图，6 组测试集各 200 张，读对 / 读错）：

| 测试集 | small / small | small 检测 + medium 识别 | medium 检测 + small 识别 | medium / medium |
|---|---|---|---|---|
| 常规 | 98.0% / 1.5% | 98.5% / 1.0% | 97.5% / 1.5% | 97.5% / 1.5% |
| 远距离（二维码 90–150 px） | 92.5% / 0% | 94.0% / 2.0% | 92.5% / 0% | 94.5% / 2.0% |
| 强模糊 | 79.0% / 3.0% | 82.5% / 3.5% | 77.0% / 4.0% | 81.0% / 3.5% |
| 弱光 + 强噪点 | 96.0% / 0% | 95.5% / 1.5% | 95.5% / 0% | 95.0% / 1.0% |
| 大倾斜 | 89.5% / 3.0% | 93.0% / 2.5% | 90.0% / 1.0% | 92.0% / 2.5% |
| 低画质视频 | 97.0% / 0% | 97.5% / 0.5% | 95.0% / 0% | 95.0% / 0.5% |
| **合计（1200 张）** | 92.0% / 1.3% | **93.5%** / 1.8% | 91.3% / 1.1% | 92.5% / 1.8% |
| 每张耗时（中位 / p90） | 203 / 226 ms | 421 / 482 ms | 541 / 564 ms | 743 / 811 ms |
| 识别时内存峰值 | 176 MB | 240 MB | 241 MB | 317 MB |
| 模型大小 | 30 MB | 82 MB | 79 MB | 132 MB |

- 大模型的收益在识别：medium 识别在模糊、倾斜、远距离时多读对 2–3.5 个百分点。medium 检测没有带来提升，还慢一倍多。
- 两档让用户选（「通用」→「文字识别速度」，设置项 `ocrModelTier`），都装在安装包里，切换不用下载：
  - **极速**（默认）：small 检测 + small 识别。
  - **精准**：small 检测 + medium 识别。安装包多带一个 medium 识别模型（73 MB）。
  - 换档时主进程放掉旧模型（正在跑的识别不受影响），按新档位加载、预热，并重新告诉手机要不要截图。
- 两档都有 1–2% 的读错，大模型没有减少读错；下一步考虑按识别置信度把低分的结果当作「没认出」，让读错变成重扫。
- 模拟和真实拍摄有差距（字体、打印质量、真实的抖动和反光），结论要用真手机扫真标签核对（验收 #57）。

内存：ONNX Runtime 默认的 CPU 内存池（arena）按见过的最大图留着内存不还，识别时峰值 253 MB；关掉后 131 MB，速度基本不变（`native/ocr/crates/ocr-core/src/inference.rs`）。
